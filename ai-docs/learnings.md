### 2026-07-13 — tooling — workspace `cargo fmt` reformatted out-of-scope sibling crates
**What happened:** Under a "geom.rs only" implementation scope (`/task` Step 8, Group A), I ran workspace-wide `cargo fmt`; it reformatted two pre-existing-unformatted files outside my scope — `crates/core/src/sim.rs` (import order, same crate as geom.rs) and `crates/ai/src/lib.rs` (signature wrap). I reverted both with `git restore`; neither was staged or committed.
**Rule:** When scoped to a single file in a multi-crate workspace, do NOT run workspace `cargo fmt` — it silently touches sibling crates. Write the target file already-formatted and VERIFY with `cargo fmt --check`, confirming the target file is ABSENT from the diff (pre-existing out-of-scope offenders may still appear, which is expected). `cargo fmt -p <crate>` is insufficient when the offender shares the target's crate.
**Kind:** correction
**Escalated?** agent:code-writer

### 2026-07-15 — code-style — integer ops must be overflow- and signedness-safe
**What happened:** During the Size/Rect/unsigned-`Corridor` rework (PR #47 follow-up to the #5 review), the `design` subagent proposed `Rect::index` with a raw `p.x - self.origin.x` subtraction, arguing the i32-overflow risk was "unchanged from today / out of scope" (same bounded-coordinate domain as `supercover`). The owner rejected this and pinned a `checked_sub` + `usize::try_from` form so `index` is total and panic-free even for adversarial i32 coords (e.g. `i32::MAX - (-10)`), then instructed: all integer ops must be safe against overflow and signedness issues.
**Rule:** Integer arithmetic and conversions in this workspace must be overflow- and signedness-safe by construction. Reach for the explicit-semantics integer methods where appropriate — such as `abs_diff`, `borrowing_sub`, `carrying_*`, `checked_*`, `overflowing_*`, `saturating_*`, `strict_*`, `wrapping_*` (illustrative, not an exhaustive list) — choosing the one that matches intent: `checked_*` → `Option`/`None` on out-of-range; `saturating_*` → clamp to bound; `wrapping_*`/`overflowing_*` → explicit modular (value, or value+flag); `strict_*` → always-panic (even in release) for a true invariant; `abs_diff` → unsigned magnitude of a difference; `carrying_*`/`borrowing_*` → multi-word chains. Raw `+`/`-`/`*`/`/` remain allowed where the operands are knowingly bounded so no overflow, signedness issue, or division-by-zero can occur — but that safety rests on an assumption, so it MUST be covered by a test that exercises the bound. For type conversions prefer `usize::try_from(i32)?` / `u32::try_from(...)` over `as` casts wherever an out-of-domain input could overflow or lose sign — `try_from` folds the negative-value guard into the conversion (no explicit `< 0` check, no `#[allow(clippy::cast_sign_loss)]`); `checked_sub` avoids the i32 subtraction-overflow panic. This reinforces gp-core's zero-production-panics target — do NOT defer overflow/signedness safety as "out of scope" when the surrounding change is already hardening the same code path.
**Kind:** correction
**Escalated?** code-style

### 2026-07-15 — process — a lint that subsumes an issue's future work → prefer `Closes` over `Refs`
**What happened:** For the #48 integer-safety audit, I set PR #54's Tracking to `Refs #48` (not `Closes`), reasoning that #48 is a "standing audit" whose deferred scaffold re-audit should keep it open. The owner challenged this ("if we added lint arithmetic_side_effects, then #48 could be closed, or leave it open endlessly?"). They were right: the same PR enabled `clippy::arithmetic_side_effects = "deny"` workspace-wide (and `pedantic` already denies the cast lints), so every future raw op / unsafe cast — in scaffolds or anywhere — is now flagged mechanically at commit/CI time. Reserve `Refs #N` for issues with genuine remaining *manual* work. Separately (candidate `/improve` escalation): have `cleanup-progress.sh` fall back to branch-name→spec-base derivation (it already receives `<previous-branch>`) so a genuinely-`Refs` PR does not orphan its progress file.

### 2026-07-16 — documentation — design-marker `[Xn]` refs in Rust doc comments must be backticked/escaped (broken intra-doc link)

(design doc §3 [D1]/[N2], ...)`. rustdoc parses `[D1]`/`[N2]` as intra-doc links; with `rustdoc::broken-intra-doc-links` denied via the `RUSTDOCFLAGS="-D warnings"` doc gate, `cargo doc` failed (`error: unresolved link to \`D1\`` / `\`N2\``). `cargo build`/`test`/`clippy` were all green — only the Step 9 doc gate caught it. ### 2026-07-16 — architecture — a new gp-core production `.expect`/`unwrap` must be weighed against the zero-production-panics invariant at design time
**What happened:** For the #10/#49 collisions task, the `design` doc specified the equidistant tie-draw as `free[rng.random_range(0..u32::try_from(free.len()).expect("layer ≤ area fits u32")) as usize]` and `design-review` GO'd it (with a documented `# Panics` section). But `gp-core` has an explicit **zero-production-panics** invariant (`ai-docs/panic-index.md` header "gp-core targets zero production panics" — the index is EMPTY; `context.md`/`README` claim zero production panics; the #48 integer-safety audit deliberately made every impossible-case op *total* via `checked_*`/`saturating_*`/`try_from`, not panicking). The `.expect` would have been the first-ever panic-index entry. Caught by `/task` Step 9's panic-index sync (build/test/fmt/clippy/doc were all green — the panic-index scan is the only thing that flags it). Fixed inline to a total form: `let n = u32::try_from(free.len()).unwrap_or(u32::MAX); free[rng.random_range(0..n) as usize]` (in the unreachable >u32::MAX-cell-layer case, caps the draw range — index still valid, no panic), removed the `# Panics` doc section, re-ran gates green. panic-index.md stays empty.
**Rule:** When designing/reviewing any new `gp-core` (`sim`/`geom`) production code, treat a proposed `.expect`/`unwrap`/`panic!`/panicking-index as a **red flag against the zero-production-panics invariant** — prefer a *total* form (`checked_*`/`saturating_*`/`try_from(..).unwrap_or(sentinel)`/`Option`) that gives defined behavior in the impossible case, mirroring the #48 integer-safety-audit posture. `ai-docs/panic-index.md` is the canonical inventory and is intentionally empty for gp-core; adding the first entry should be a deliberate, justified exception, not an incidental `.expect`. `design`/`design-review` should check new gp-core panics against this invariant before GO, not leave it to the Step 9 panic-index sync to catch.
**Kind:** correction
**Escalated?** agent:design, agent:design-review

### 2026-07-16 — search — `find`/`ls` proves on-disk presence, NOT git-tracked status; verify with `git ls-files` / `git check-ignore`
**What happened:** During the #11 render-backend interview the user asked me to inspect how golden tests are done in the sibling repo `../quartzite`. A `find . -name '*.png'` listing returned `quartzite-style/tests/snapshots/vulkan/*.png`, and I reported to the user that quartzite "commits its goldens as plain PNGs", citing that path, and speculated that "goldens appear keyed by backend". A follow-up `Explore` subagent found both claims wrong: `.gitignore:12` ignores `**/tests/snapshots/vulkan/` (verified `git check-ignore -v` → `.gitignore:12`), so those files are **untracked local regen debris** (116 stale files in `auto/` + 59 in `vulkan/`); only `shared/` is tracked (`git ls-files` → 65 PNGs, 100% under `shared/`). The conclusion I stated (plain git, no LFS, no `.gitattributes`) happened to be true for the `shared/` set, so the error was invisible in the outcome — I reached a right answer from wrong evidence. **Rule:** `find` / `ls` / `rg --files` answer "does this path exist on disk", never "is this path committed". Applies with extra force to a sibling/reference repo being mined for precedent, where untracked scratch output is exactly what a naive listing surfaces first — and where a wrong "they do X" claim propagates into a spec as a false precedent.
**Kind:** correction
**Escalated?** AGENTS.md, agent:spec-writer

### 2026-07-16 — search — `git status` is BLIND to ignored files; "0 untracked" ≠ "nothing there" (inverse of the find/ls trap)
**What happened:** Round 5 of the #11 interview, the `spec-writer` subagent checked whether quartzite's stale snapshot-regen debris was real and reported "the current working copy shows **0/0**, so that count did not reproduce", and wrote that into the spec (`2026-07-16-render-backend-decision.spec.md:247`) as a parenthetical retraction. It is false. Re-verified directly: `ls quartzite-style/tests/snapshots/auto/*.png | wc -l` → **116**; `vulkan/` → **59**; `shared/` → **95** (60 tracked + 35 `.actual`/`.diff` artifacts). The cause: `git status --porcelain <path>` returns **0** for those files because they are gitignored (`git check-ignore -v` → `.gitignore:11:**/tests/snapshots/auto/`), and `git status` suppresses ignored entries by default. `git status --porcelain --ignored` reveals them (37 entries — dirs collapse to one `!!` row each). The subagent's method could not see the category it was asked about, so absence-of-signal was misread as evidence-of-absence. This is the **exact inverse** of the earlier entry this same session ([[2026-07-16 — search — find/ls proves on-disk presence, NOT git-tracked status]]): there, `find` saw ignored files and I called them committed; here, `git status` couldn't see ignored files and the agent called them gone. Both are "used a tool blind to the asked-about category, then asserted a fact".
**Rule:** Match the query tool to the FILE CATEGORY being asked about, and state the category explicitly before choosing: **tracked** → `git ls-files <path>`; **ignored (and by which rule)** → `git check-ignore -v <path>`; **untracked-but-not-ignored** → `git status --porcelain`; **ignored included** → `git status --porcelain --ignored`; **exists on disk at all** → `ls` / `find`. `git status` returning empty proves only "no untracked-and-unignored changes" — it is NEVER proof a path is absent, and is actively misleading for any question about `.gitignore`d build/regen output, which is precisely where stale-artifact questions live. Corollary for agents relaying a report: when a subagent RETRACTS a figure from an earlier investigation, re-verify the retraction with a category-correct command before letting it into a spec — a retraction is an assertion too, and this one would have shipped a false claim that *understated* the case it was cited to support.
**Kind:** correction
**Escalated?** AGENTS.md, agent:spec-writer

The failure mode was **silent**: an implementor obeying its own contract skips the spawn, the PNG commits unchecked, and every gate stays green (the agent file exists, so an AC-spot-check passes) — the exact `SKIP_RENDER_SNAPSHOT`-style silent no-op the spec was written to prevent. Resolved by a product-owner-approved narrow carve-out (permitted: a subtask-named *artifact-validity* check verifying a generated artifact against the code that generated it — the `cargo test` category, which `code-writer` already runs freely; still forbidden: `self-review` and any approval-gate reviewer judging the *work*). A `tools: *` inherit-all grant is evidence about (1) and says **nothing** about (2). The harness's `.claude/agents/*.md` and `.claude/skills/**` files are as much a source-of-truth as a crate's `src/` — apply the same read-the-source discipline the [[2026-07-16 — search — find/ls proves on-disk presence, NOT git-tracked status]] and [[2026-07-16 — search — git status is BLIND to ignored files]] entries demand for VCS state. Tell: if a plan says "X spawns Y" and the justification cites only X's *tools*, the permission check has not been done. Highest-risk shape: the violation is **silent** (the callee is simply never invoked) rather than an error, so no gate catches it.
**Kind:** correction
**Escalated?** agent:design, agent:design-review

### 2026-07-16 — tooling — the project's own crates.io recipe silently returns `null`: the API now requires a User-Agent
**What happened:** #11 Group A subtask 4 needed the live `max_stable_version` for `egui`/`eframe` before writing `"0.35"` into `ai-docs/key-decisions.md`, per the AGENTS.md § *Dependency Versions* AXIOM. Run **verbatim as the project documents it** (`curl -sS "https://crates.io/api/v1/crates/X" | jq -r '.crate.max_stable_version'` — AGENTS.md's trigger table and `ai-docs/dependency-versions.md:13`), it returned **`null`** for all four crates (`egui`, `eframe`, `egui_kittest`, `egui-wgpu`). The bare `curl` sends no `User-Agent`, and crates.io refuses such requests under its API data-access policy, replying with an error *body*: `{"errors":[{"detail":"We are unable to process your request at this time. This usually means that you are in violation of our API data access policy (https://crates.io/data-access) …"}]}`. That body is valid JSON with no `.crate` key, so `jq -r '.crate.max_stable_version'` prints the literal string `null` and **exits 0**. Re-running with `-H "User-Agent: graphite-gp-agent (<contact-email>)"` returned `0.35.0` instantly. The failure is silent in the worst way: the recipe emits a plausible-looking *value* instead of an error, and `null` reads as "no stable version" / "crate not found" — a fact-shaped non-answer. Had I taken it at face value the entry would have been "no stable release found", or I would have fallen back to the remembered version, which is exactly what the AXIOM exists to prevent.
**Rule:** Every crates.io API call MUST carry a `User-Agent` identifying the caller (crates.io's data-access policy requires one): `curl -sS -H "User-Agent: <project> (<contact-email>)" "https://crates.io/api/v1/crates/<name>" | jq -r '.crate.max_stable_version'`. Treat a `null` from any version lookup as **"the query failed"**, never as data — re-run without the `jq` filter and read the raw body before concluding anything. Generalises beyond crates.io: whenever a verification recipe pipes an HTTP response through `jq`, a policy / auth / rate-limit error body is *still valid JSON*, so `jq` prints `null` and exits 0 — the pipeline reports success while the fact was never obtained. Same shape as the two `search` entries above (a tool blind to the asked-about category, then an assertion), but landing on the **verification AXIOM's own tooling**: a stale recipe defeats the AXIOM as thoroughly as not running it, and more quietly, because the operator believes a check ran. Tell: a version lookup returning `null` for a crate you have good reason to believe is published is a **tooling** failure until proven otherwise, not a fact about the crate.
**Kind:** correction
**Escalated?** AGENTS.md, hook — the recipe itself was repaired in AGENTS.md § *Dependency Versions* and in `ai-docs/dependency-versions.md` (an ai-docs reference page has no `Escalated?` enum token of its own); the new `crates-io-ua` PreToolUse hook in `.claude/settings.json` blocks the UA-less form mechanically

### 2026-07-16 — documentation — a DOC-1 tense fix can trip `clippy::too_long_first_doc_paragraph`; "one-character fix" is not a gate-free fix
**What happened:** `/task` #11 Step 10, `self-review` returned REJECT on a `major`: `crates/render/src/placeholder.rs:109`'s summary line read *"**Draw** the scaffold placeholder frame into `rect`: …"*, violating `ai-docs/doc-convention.md` DOC-1 (third-person present indicative). It correctly noted *"Fix is one character"* — add the `s`. It was one character, and it **broke the build**: the first doc paragraph was sitting one char under `clippy::too_long_first_doc_paragraph`'s limit, so `Draw`→`Draws` tipped it over, and that lint is **denied workspace-wide via `[workspace.lints.clippy] nursery = "deny"`**. `cargo build`, `cargo test` (103), `cargo fmt --check` and the `RUSTDOCFLAGS="-D warnings"` doc gate ALL still passed — only `cargo clippy --workspace --all-targets -- -D warnings` caught it (`could not compile gp-render (lib) / (lib test)`). **Rule:** Re-run the **full** gate set after *every* Step-11 review fix, including fixes an agent (or you) calls trivial — "one character", "just a typo", "doc-comment only". Doc comments are compiled input: `clippy::nursery` (denied here) polices their *shape* (`too_long_first_doc_paragraph`, `doc_markdown`, `missing_panics_doc`), so a prose edit can fail clippy while build/test/fmt/**and the doc gate itself** stay green — `cargo doc` does NOT subsume `cargo clippy` for doc-comment lints. Corollary when fixing a DOC-1 tense violation on a long summary: prefer **restructuring to a short first paragraph + blank `///` + details** over inserting the verb suffix in place; the insertion is the form that trips the length lint, and the restructure satisfies DOC-1's summary-line intent directly. Corollary for reviewers: a fix's *size* is not evidence of its *risk* — "fix is one character" is a claim about the edit, never about the gates.
**Kind:** correction
**Escalated?** agent:code-writer, skill:task

### 2026-07-16 — testing — an FFI/GPU test aborts the ADVISORY workspace Miri job, losing its own crate's binary + every phase queued behind it
**What happened:** PR #70 (#11 render backend) added `gp-render`'s `golden_guard`, which drives wgpu → `dlopen`s the Vulkan ICD via `libloading`. The CI `miri` job (`cargo miri test --workspace`, `MIRIFLAGS=-Zmiri-tree-borrows`) aborted: `error: unsupported operation: can't call foreign function 'dlopen' on OS 'linux'` → `error: aborting due to 1 previous error`. **Miri had been green on main's last three runs including the base commit** — this PR turned it red. Every REQUIRED check passed and the PR stayed `MERGEABLE`, because the job is `continue-on-error: true` ("Advisory only — no `miri-pass` gate is wired into branch protection"), so nothing blocked and it would have been easy to shrug off. **What the abort actually cost (measured from the failing job's log, NOT assumed):** the binary order was `gp_ai → gp_core → graphite_gp → gp_gen → gp_render`, and `gp_core` reported `97 passed; 0 failed` at 17:06:58 — **four seconds before** gp_render's abort at 17:07:02. So gp-core's coverage was never lost, and nothing was silent: the job went red, which is how it was found. What WAS lost is gp-render's own binary (both tests, `tessellation_smoke` included) plus every phase cargo's fail-fast skipped behind it — the doc-test phase never started — **zero** `Doc-tests` lines in the failing log, against `Doc-tests gp_core → 2 passed` once fixed. gp-core survived on **binary ordering, not by design**: a future FFI test in an earlier-scheduled crate would take the later ones with it. The standing cost is the red mark itself — a permanently-red advisory job is one nobody reads, the same rot mechanism as quartzite's all-black goldens. Fixed surgically with `#[cfg_attr(miri, ignore = "…")]` on `golden_guard` alone (NOT `--exclude gp-render`, which would also have dropped the CPU-only `tessellation_smoke`): verified locally with the exact CI command — `cargo +nightly miri test --workspace` exit 0, 97 gp-core + 2 gp-gen + `tessellation_smoke` **passing under Miri**, only `golden_guard` ignored with its reason printed. Precedent: quartzite hit this class three times (`miri-deny-list`, `miri-subset-widening`, `miri-master-push-job` plan pairs) — its trigger was `nv-flip`'s C FFI, ours is `dlopen`; same shape.
**Rule:** When adding a test that touches **FFI, a GPU, `dlopen`, or any foreign function** (wgpu / vulkan / a `-sys` crate / `libloading`), gate it with `#[cfg_attr(miri, ignore = "<why>")]` **in the same commit**. Miri aborts the `--workspace` run at the first unsupported op and cargo's fail-fast drops every phase queued behind it, so the blast radius is the offending crate's whole binary plus the later phases (doc-tests especially) — and any crate whose unittest binary happens to be scheduled after it. **Measure the blast radius from the log before claiming it**; crates scheduled earlier complete normally, and asserting otherwise puts a mechanism that does not exist into the feed `/improve` escalates into AGENTS.md. Prefer the **per-test attribute** over a crate-level `--exclude` in `ci.yml`: it keeps that crate's non-FFI tests under Miri (`tessellation_smoke` really does run), states the reason at the site where a future reader hits it, and prints "ignored, <reason>" in the run output instead of silently omitting the test.
