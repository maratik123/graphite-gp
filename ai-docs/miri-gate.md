# Miri gate — detail

> Full mechanics of the workspace Miri gate plus the two mechanical `gp-render` gate triggers. The fail-loud summary lives in [`AGENTS.md` § Rust Test Conventions](../AGENTS.md#rust-test-conventions); this page is the on-demand reference detail.

- **Miri aborts on the FIRST unsupported operation**, and cargo's fail-fast then drops every phase queued behind it — the offending crate's whole test binary plus the doc-test phase. Gate any test that can abort Miri with `#[cfg_attr(miri, ignore = "<why>")]` **in the same commit**. Per-test, **never** a crate-level `--exclude` (that also drops the crate's Miri-clean tests). The trigger is **"aborts under Miri", NOT "is FFI"** — the two in-tree gates have unrelated causes: a **wgpu golden** (e.g. `app_shell_matches_golden`, `crates/render/src/app_gallery.rs`) drives wgpu and `dlopen`s the Vulkan ICD (FFI), while `tessellation_smoke` (the sibling in the same file) has **no FFI** and aborts because drawing text runs `vello_cpu`'s checked `u8`→`u32` pixmap cast, which panics under Miri's 1-byte allocator alignment. Write the reason for **that test's own** abort; do not copy a sibling's — a wrong reason is a false justification for a different failure. Reproduce with the **workspace** command CI runs (`MIRIFLAGS=-Zmiri-tree-borrows cargo miri test --workspace --exclude gp-gen --exclude gp-game`; locally add `+nightly` to select the toolchain that has `miri`), never a narrower `-p` run. **`gp-gen` and `gp-game` are both excluded from the workspace Miri gate** — these are the **two sanctioned crate-level `--exclude`s**, and both are *cost* carve-outs, **not** correctness ones. `gp-game` is excluded under [#184](https://github.com/maratik123/graphite-gp/issues/184): since #43 it is the orchestration crate, so its generation worker spawns real threads, its persisted replay format does real file I/O, and its CLI-contract tests spawn the built binary. Each is gateable per test, but the list would grow with nearly every new test and **one** missed attribute aborts the whole crate binary (Miri fails fast on the first unsupported operation) — turning an easy omission into a red workspace gate. The workspace has **zero** production `unsafe`, and the crate that most warrants the UB pass — `gp-core` — stays in the gate and is green. A new `gp-game` test therefore needs **no** `#[cfg_attr(miri, ignore)]`, but existing ones are **kept**, not stripped: they are correct, they document why the test is Miri-hostile, and they are what #184's re-enable path needs. As for `gp-gen`, it is a *cost* carve-out, **not** a correctness one: `gp-gen` is pure-integer and Miri-clean, but its multi-seed generator property sweeps (Ф1/Ф2/Ф3, dozens of seeds × the whole pipeline) regressed the workspace Miri wall-clock from ~2 min to >1 h under the interpreter, tracked by [#134](https://github.com/maratik123/graphite-gp/issues/134). It stays excluded **until #134 resolves** (the re-enable plan is a small gated seed sweep behind `#[cfg(miri)]`); until then a new `gp-gen` test needs **no** `#[cfg_attr(miri, ignore)]` (the crate never runs under CI Miri), and you must reproduce with **both** `--exclude gp-gen --exclude gp-game` locally, or the run will hang for an hour. These two carve-outs (`gp-gen` #134, `gp-game` #184) are the **only** exceptions to the per-test-`ignore`-**never**-`--exclude` rule; every **other** crate stays per-test. **A red Miri is a REGRESSION TO FIX, but does not currently block merge** ([#76](https://github.com/maratik123/graphite-gp/issues/76), resolved 2026-07-18). The `miri-pass` aggregator produces the **`Miri`** context (`ci.yml`, `if: always()`, mirrors `build-pass`) and the raw `miri` job's `continue-on-error` was **removed**, so a red Miri fails the job → workflow run → aggregator. Because the run itself goes red, `gh run list` **does** reflect a red Miri (the earlier *"`gh run list` is blind to a red Miri"* caveat no longer holds). **But `Miri` is deliberately NOT among `main-protection`'s required contexts** — verified 2026-07-25 via `gh api repos/maratik123/graphite-gp/rules/branches/main`, the required set is `Build`, `Clippy`, `Docs`, `Format`, `Test`. The gate is held out of branch protection **while its wall-clock is long**, pending [#134](https://github.com/maratik123/graphite-gp/issues/134) for `gp-gen` plus further per-crate tuning; restore `Miri` to the required set once those land. A path-filtered `skipped` Miri (a non-Rust PR) still passes the aggregator. Treat a red Miri as a **regression to fix** — green it, or `#[cfg_attr(miri, ignore)]` the aborting test per the rule above, before merge; branch protection not enforcing it does not relax the discipline. Check it after any PR adding a new dependency class.
- **gp-render Context/painter unit tests carry the Miri gate — mechanical trigger.** Any `gp-render` unit test that constructs an `egui::Context` (`Context::default()`) or drives a painter (`run_ui`/`layer_painter`), directly OR through a shared capture helper (`render_shapes`, `painted_shape_count`, `painted_meshes`), MUST carry `#[cfg_attr(miri, ignore = "<why>")]`, mirroring the wgpu-golden gate above. The trigger is *constructs a Context/painter* — grep-checkable (`rg -Un 'egui::Context::default' crates/render/src`, then confirm each enclosing `#[test]` is gated), NOT "is slow": these are interpreted wall-clock **cost**, not abort. Give one honest reason per helper-group — same-helper siblings share **one** cause and MAY share a reason; the "don't copy a sibling" rule above is about *different* causes, not same-cause tests.
- **gp-render zero-production-UB-signal token/helper tests carry the Miri gate — mechanical trigger.** Any `gp-render` unit test whose body asserts ONLY **(a)** constant/data parity against a static source (the `include_str!`'d design-system CSS consts — `tokens::{color,spacing,typography,effects}` + `mod inventory`) **or (b)** `#[cfg(test)]`-only helper machinery never linked into the game binary (the `pub(crate) mod css` parser, the `mod test_util` `assert_f32`/`assert_f32_slice` helpers) MUST carry `#[cfg_attr(miri, ignore = "<why>")]`. Its Miri UB coverage is worthless (pure safe-Rust parity, or test-only scaffolding), so gate it — grep-checkable (`rg -Un '#\[test\]' crates/render/src/tokens crates/render/src/test_util.rs`, then confirm each enclosing `#[test]` is gated), NOT "is slow": like the Context/painter gate these are interpreted wall-clock **cost**, not abort — the reason must make **no abort claim**. One honest reason per cause-group (constant-parity / css-parser / test_util); same-cause siblings MAY share it.
- **Local Miri is EXCEPTION-ONLY — on cost grounds, not policy grounds.** Do NOT run the workspace Miri gate locally as routine per-subtask verification (`/task` Step 8), and do NOT write such a step into a design doc. The first Miri build after any new dependency edge rebuilds the workspace under the interpreter and can run for tens of minutes producing no file writes and no live `cargo`/`rustc`/`miri` process — indistinguishable from a hung subagent. Local Miri needs a **STRONG, NAMED** reason: diagnosing an already-red Miri run, or deciding whether a test genuinely **ABORTS** the interpreter (vs merely costing wall-clock) before writing its `#[cfg_attr(miri, ignore = "<why>")]` reason. What is dropped is the local **reproduction**, never the gating requirement — the per-test `#[cfg_attr]` in the same commit stays mandatory. The "reproduce with the workspace command CI runs" rule above governs the **SHAPE** of a Miri run you have already decided to make; it is **not** a mandate to make one. When a long Miri build IS warranted, say so up front — silence with no live process looks identical to a hang.
