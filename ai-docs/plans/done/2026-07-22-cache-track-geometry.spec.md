# Cache track geometry (eliminate per-frame re-triangulation)

**Source:** issue #104
**Date:** 2026-07-22
**Tracked in:** #104

> **AMENDMENT (2026-07-22, product-owner-directed pivot after design-review GO + 3 implementation subtasks).** The original approach cached the triangulated mesh keyed on `(track identity, rect)` — a memoized `&mut Option<TrackGeometryCache>` handle rebuilt whenever the render rect changed — because the triangulation was assumed rect-dependent. **That assumption is now known false and the approach is superseded.** The triangle *topology* (indices `Vec<[u32; 3]>`) is a pure function of the track's lattice-space shape, invariant under the render rect; `TrackTransform` (`crates/render/src/track/transform.rs:82`) is a plain affine map (uniform scale + translate + y-flip) that only repositions vertices — it never changes which triangles tile the polygon. This spec is rewritten to key the cache on **track identity only** (no rect, no rect-invalidation): geometry is built once per track and, per frame, only the cheap `O(n)` lattice→screen vertex map runs. See *Key decisions* → "Why this amends the original rect-keyed cache".

## Scope

1. Introduce a public **track-geometry** type in `gp-render` that holds the precomputed, **rect-independent** static geometry for one race, keyed on **track identity only**: the chained, Chaikin-smoothed wall loops (`smoothed_loops`, lattice space), the outer/hole role split (`loop_roles`), and each loop's **triangulation indices** (`Vec<[u32; 3]>` — topology only, lattice-space triangulation). All three are **pure functions of `&TrackArtifact`**; none depends on the render `Rect` or `TrackTransform`.
2. Expose a **pure builder** (a `fn` / associated `new`) from `gp-render` that produces the geometry from `&TrackArtifact` alone. The value is **owned, instantiated, and invalidated by the caller** (`gp-game`'s app state), not stored as frame-to-frame state inside `gp-render` — mirroring the fonts precedent (`gp-render` produces `FontDefinitions`; `gp-game` calls `set_fonts`), consistent with `gp-render`'s draw-only / stateless invariant (`ai-docs/key-decisions.md` 2026-07-16).
3. Per frame, the draw path maps each loop's lattice verts → screen `Pos2` through `TrackTransform` (`O(n)`, cheap) and draws with the **stored indices**. No per-frame re-triangulation and no per-frame `chain_walls` / `chaikin_smooth` / `classify_loops`. Thread the baked geometry into `render_frame` / `draw_frame` and down to `regions::fill` and `heatmap::paint`.
4. Eliminate `heatmap::paint`'s redundant *second* triangulation pass by reusing the same baked indices `regions::fill` uses.
5. The caller rebuilds the geometry **only when the `TrackArtifact` changes**. A window resize / rect change triggers **no rebuild** — only the per-frame re-map — which is strictly better than the superseded "rebuild on rect change".
6. The change is **behavior-preserving**: the drawn output is byte-identical (every committed golden unchanged).
7. Update the AC-tagged test suites touched by the API change — in `track/mod.rs`, `track/regions.rs`, `track/heatmap.rs`, `track/geometry.rs` — to the new rect-free baked-geometry APIs, and add coverage for the no-recompute / single-triangulation / resize-does-not-rebuild properties.
8. Wire `gp-game` to own, build, and invalidate the geometry for both the Race and Lab canvases (both call `render_frame` today via `AppShell.show`), rebuilding on track swap only.

## Out of scope

- `find_ear`'s O(n²)-per-ear linear scan (`regions.rs`) — converting to a doubly-linked-list ear-clipping structure for O(1) vertex removal. Secondary/optional per the issue; the primary win is eliminating unconditional per-frame re-triangulation, which dwarfs the triangulator's constant factor.
- `Corridor::len()` / `is_empty()` O(width×height) full scans (`crates/core/geom/mod.rs`) — a maintained drivable-cell counter. Not on any hot path; flagged in #104 as a separate issue if pursued.
- Caching the cheap per-frame layers (walls stroke, `grid`, S/F chord, cars). Only the region/heatmap triangulation pipeline is the cost target.

## Deferred
- `find_ear` O(n²)→O(1) DLL ear-clipping | constant-factor improvement, dominated by the per-frame re-triangulation this spec removes | revisit only if the baked geometry alone does not suffice — separate issue if pursued
- `Corridor::len()`/`is_empty()` maintained counter | not on any hot path | separate issue (already flagged in #104's "Also flagged" note)

## Key decisions

| Question | Decision |
|---|---|
| What is the cache keyed on? | **Track identity only** (amended). The baked geometry — `smoothed_loops`, `loop_roles`, and per-loop triangulation indices — is a pure function of `&TrackArtifact`, invariant under the render rect. No rect in the key; a resize does not invalidate it. |
| Why does this amend the original rect-keyed cache? | The triangulation *topology* (`Vec<[u32; 3]>`) is immutable against the render rect: `TrackTransform` (`transform.rs:82`) is a plain **affine** map (uniform scale + translate + y-flip) that only repositions verts, never re-tiles the polygon. The superseded approach mapped lattice→screen **first** then triangulated (`regions::triangulated_loop`, `regions.rs:377`), which *falsely* coupled the O(n³) ear-clip to the rect and forced a rebuild on every resize. Triangulating in **lattice space** yields rect-free indices; per frame only the O(n) `transform.map(vertex)` remains. |
| What does the baked geometry store? | `smoothed_loops` (lattice-space vertex pairs), `loop_roles` (outer/hole split), and per-loop triangulation **indices** (`Vec<[u32; 3]>`, topology). It stores **no** `rect`, **no** `TrackTransform`, and **no** screen-space `Pos2` verts — those are per-frame outputs of the draw path's O(n) map. |
| Where does the geometry type live? | In `gp-render` — it holds `gp-render`'s `regions::LoopRoles` and its Chaikin/triangulation output. `gp-render` exposes a public type + pure builder; the caller stores the instance. It is **not** placed inside `gp-core`'s `TrackArtifact` (`crates/core/src/track.rs:329`): the physics core is integer-only and deterministic (`docs/design.md` §3a) and must not depend on `gp-render` or hold render-space vertex data. |
| Who owns / invalidates the geometry? | The caller (`gp-game`), rebuilding on **track swap only**. `gp-render` stays draw-only: no new normal dependency, no frame-to-frame internal cache state (`key-decisions.md` 2026-07-16). |
| Cache = input or internal state? | One more **input** to `render_frame` / `draw_frame`, not internal state — keeps `draw_frame`'s "pure function of its inputs" contract (`lib.rs` / `mod.rs` doc, issue text). The rect stays a separate draw parameter; the baked geometry is rect-free. |
| `find_ear` micro-opt in this task? | No — deferred (see Out of scope / Deferred). |

## Technical constraints

- **Render path is LIVE (issue body is stale here).** The issue states rendering "isn't live yet — `gp-game`'s `main.rs` still calls `draw_placeholder`". Verified false as of 2026-07-22: `draw_placeholder` no longer exists in the tree, and `main.rs` → `AppShell.show` → `Race`/`LabScreen` → `crate::render_frame` runs the full triangulation pipeline **every frame**. The current fixture track is small (a hand-built rounded-rect loop), so the cost is latent until real generated tracks (block 1) land — but the redundant pipeline executes on every frame today.
- **The rect-availability wrinkle is DISSOLVED (amended).** The superseded spec called out that the canvas `rect` is computed *inside* `gp-render` (`race.rs` / `lab.rs` `draw_canvas`), unknown to `gp-game` before `shell.show`, forcing a `&mut Option<Cache>` memoized-handle model to build the mesh where the rect is known. With the amended design the baked geometry **needs no rect at build time** — it is built from `&TrackArtifact` alone, before `shell.show`, as a plain caller-owned `&Cache` input. The rect only enters the per-frame O(n) map inside the draw path. The `&mut Option<Cache>` vs `&Cache` open question no longer applies.
- **Winding / diagonal choice must be VERIFIED, not assumed (load-bearing).** The affine `TrackTransform::map` (`transform.rs:82`) applies a **y-flip** (its screen-y term is `-cell_size`), i.e. a negative-determinant map that reverses polygon winding. Ear-clipping may therefore pick **different diagonals** triangulating in lattice space vs the former screen space. This is acceptable because a valid triangulation of a polygon, mapped affinely, is still a valid triangulation of the mapped polygon, and egui raw-mesh fills are **not edge-feathered** — the raster is identical for *any* valid triangulation of the same silhouette. But this must be **verified** (goldens re-compared byte-identical, AC6), never assumed, since the specific diagonals differ. If a golden shifts, the fill has a real triangulation bug (e.g. a degenerate/inverted ear under the flipped winding), not a benign diagonal swap.
- **`gp-render` draw-only invariant.** No `eframe`/`winit`/`wgpu` normal dependency; the baked geometry adds no new normal dependency to `gp-render` and no persistent internal state (`key-decisions.md` 2026-07-16). The integer-only, deterministic physics layer is untouched — all baked geometry is `gp-render`-side (lattice-space vertex pairs + triangulation indices) and lives entirely in `gp-render`.
- **Miri gate (mechanical).** Any new or changed `gp-render` unit test that constructs an `egui::Context` / drives a painter (in `mod.rs`, `regions.rs`, `heatmap.rs`, `geometry.rs`, directly or via `render_shapes` / `painted_meshes` / capture helpers) MUST carry `#[cfg_attr(miri, ignore = "…")]` per the standing rule; a red Miri blocks merge. Pure lattice/screen-space geometry tests over a hand-built `TrackArtifact` fixture that build no `Context` and drive no painter do **not** need the gate.
- **API breakage is fine.** Game app, never published — `render_frame` / `draw_frame` / `regions::fill` / `heatmap::paint` and the amended cache type signatures change cleanly, all call sites (`gp-render` screens, `golden.rs`, `gp-game`) updated in the same change; no shims. The already-landed `TrackGeometryCache::get_or_build(&mut slot, track, rect)` rect-keyed API is replaced outright by the rect-free builder — the `rect`/`transform` fields and the `get_or_build` staleness path are removed.

## Open questions

- **Per-frame screen verts: map-on-the-fly vs a small rect-keyed vertex buffer.** The draw path must produce screen `Pos2` verts each frame from the baked lattice verts + the current `TrackTransform`. Whether it maps on the fly every frame, or memoizes a small rect-keyed screen-vertex buffer (rebuilt only when the rect actually changes, indices untouched) to skip the O(n) map on unchanged-rect frames, is a **design** detail. The primary win (no per-frame O(n³) re-triangulation) holds regardless; design decides whether the O(n) map is worth memoizing.
- **Placement in `Scene` vs a separate `render_frame` parameter.** `Scene` bundles the frame-immutable canvas inputs. The baked geometry is now rect-free (unlike the superseded rect-keyed cache), which removes the earlier "cache depends on rect but `Scene` excludes rect" tension — it could ride in `Scene` cleanly. Whether it joins `Scene` or rides as its own parameter is a design call.
