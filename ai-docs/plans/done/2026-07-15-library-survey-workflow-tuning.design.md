## Approach

Five independent parts, one PR, 36 ACs. Almost all work is instruction-file / markdown editing plus one new survey report and three near-term GitHub issues; the only candidate code surface (`gp-core`) has a **confirmed-empty** adopt-now set, so PART 1 ships no `*.rs` refactor.

### Decomposition strategy — organize by FILE, fold parts together per file

PART 2, PART 3, and PART 5 all edit the **same** Task/Design files (`design.md`, `design-review.md`, `context-reset/SKILL.md`, `task/SKILL.md`). Editing one file from several subtasks invites line-drift and merge hazards. The design therefore **consolidates all edits to a given file into one subtask** and folds the relevant PART-2/3/5 content together there. Concretely: every `design.md` change (PART 2 size caps + worked examples + `>15`; PART 3 risk-item removals at `:25`/`:43`; PART 5 Amendment C) lands in one subtask; likewise for `design-review.md`. Cross-file *concerns* (e.g. "remove the API-stability requirement") are satisfied across whichever file-subtasks own those files, tracked in the Test Design AC map.

Independent concerns that touch disjoint files get their own subtasks (PART 1 report/issues; CI-2 Review-group; DOC core; code-style ladder; AGENTS.md CI cluster; AGENTS.md API-Stability reframe). A final cross-cutting subtask runs the propagation sweeps, the `wc -c` cap gate, and the full gate battery.

### This task's OWN grouping runs under CURRENT rules (not the mechanism it writes)

The PART-5 per-group model+effort mechanism (change-type homogeneity, `sonnet`/`opus` marking, group-minimization, size-cap 10, default-4) is **content this PR writes into the harness for FUTURE `/task` runs**. It does **not** govern this task's own decomposition. Per the spec META cap-waiver (spec line 9), this task's Handoff plan runs under the **current** rules: non-terminal groups exactly **3** subtasks, terminal `1..=3`, and **every** group fans out through the current `/context-reset` `general-purpose` spawn on **Opus**. The groups below are **not** marked `sonnet`/`opus` — the per-group model-selection mechanism is inert until this PR merges. The cap-waiver explicitly permits the resulting group count (>3 groups) and subtask count (>7); **no issue-split is proposed**.

### Resolved open questions (recorded here so the design's `## Open questions` stays near-empty)

- **PART-5 spawn mechanism → inline `model=`/effort override on the existing `general-purpose` per-group spawn.** Rejected: a dedicated implementor agent file. Rationale: agent-file frontmatter `model` is **static** and cannot vary per group, but the whole requirement is per-group variation (code group → `sonnet`+`medium`; instructions group → `opus`+inherited effort). Expressing that needs an inline override at the spawn site (`context-reset/SKILL.md` step 3 already spawns `Agent(subagent_type="general-purpose", …)`). Two dedicated files (`implementor-sonnet` / `implementor-opus`) would duplicate the "read progress, run the group's subtasks, commit each" contract that `general-purpose` + the progress file already fulfil, still could not set effort without inline args, and violate YAGNI. The quality-gate subagents (`design`/`design-review`/`self-review`/`spec-writer`) keep their static `model: opus` frontmatter — only the `general-purpose` implementor spawn takes the inline override (AC25).
- **PROC-1 placement → `spec-writer.md`.** Rejected: `interview/SKILL.md`. Rationale: PROC-1 is a spec-**content** correctness rule ("issue bodies are candidate-truth; verify/embed live external version/schema/API facts before writing them into the spec"). The `spec-writer` subagent owns all spec writes and already has a "Read before drafting" preflight and a Rule-5 dep-presence check; verifying external sources before embedding them is a drafting-time duty that belongs to the drafter. The `interview` orchestrator is explicitly "plumbing only" (never drafts/edits spec content), so a content-verification step there would violate its role. Placing PROC-1 in `spec-writer.md` also lets it compose with the CI-4 live-state verification going into `AGENTS.md § Dependency Versions`. The Interview sync-group (`interview/SKILL.md`) is checked for coherence; it needs no mirrored rule (it references, not embeds, the drafting rules).
- **PROC-2 placement → `AGENTS.md § Workflow` one-liner** (the gh/commit-rule cluster), the durable workspace-wide home (every skill and ad-hoc `gh --body` call is affected, not one skill). The spec permits "`learnings.md` or the relevant skill"; a durable AGENTS.md workflow note is a superset capture of the same nugget and avoids the `learnings.md` Boundary-rule-2 dance. Folded into the AGENTS.md-CI subtask, whose grep sweep already covers `git commit` / `--body` references.
- **DOC-10 reframe-vs-remove (item 22 / AC37) → uniform REMOVE at all four sites.** Rejected: reframe-in-place to a pre-publish reminder. Rationale: the four references (`design-review.md:34-35`, `self-review.md:110-111`, `review-findings.md:93-94`, `project-review/SKILL.md:162-163`) are **per-PR / per-branch reviewer checks** that enforce Pattern A/B/C + Family C §3 — the docs.rs-self-sufficiency-now stance DOC-9 rejects. Two independent reasons to remove rather than reframe: (a) the check as written would flag the `docs/design.md §N` design-doc citations DOC-9 explicitly **retains** until first publish — it actively contradicts DOC-9; (b) "strip before first `cargo publish`" is a **one-time future action**, not a per-PR gate, so a reviewer checklist is the wrong home — it would never fire until the single pre-publish moment and only adds noise. The pre-publish strip reminder therefore lives **once** in `doc-convention.md`'s DOC-9 note (subtask 13), and the four reviewer checks are removed outright. `project-review/SKILL.md:162-163` are two gate-checklist rows that only point at `review-findings.md §6`'s now-deleted bullets, so they become dangling and are removed with them. Removal is self-contained (no dependency on the DOC-core rewrite — dropping a check that names a non-existent section is always safe). Applied **consistently** across both the Review sync-group (`self-review.md` / `review-findings.md` / `project-review/SKILL.md`, subtask 12) and the Task/Design sync-group (`design-review.md`, subtask 4).
